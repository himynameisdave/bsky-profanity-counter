# profanity.accountant

A Bluesky bot that counts how much profanity a user has posted. Node + TypeScript (ESM),
Prisma for the database, pnpm for packages, vitest for tests.

## Before you call anything done

Every change must pass all four of these locally, in this order:

```bash
pnpm format:check   # oxfmt
pnpm lint           # oxlint, --deny-warnings
pnpm typecheck      # tsc --noEmit, over src/ and test/
pnpm test           # vitest run
```

CI (`.github/workflows/ci.yml`) runs these on every PR, then `pnpm test:order` (every test file
in one worker, shuffled with a fixed seed, to catch state leaking between files) and `pnpm build`.
A `pre-commit` hook (`.githooks/pre-commit`, wired up by the `prepare` script) runs the format and
lint checks before any commit lands. Do not bypass the hook with `--no-verify`.

`tsconfig.json` covers `src/` and `test/` and never emits. `pnpm build` compiles just `src/`
to `dist/` with `tsconfig.build.json`. If you touch either tsconfig, run `pnpm build` too.

## Linting and formatting

- Lint config lives in `oxlint.config.ts`, extending
  [`@himynameisdave/oxlint-config`](https://www.npmjs.com/package/@himynameisdave/oxlint-config)
  (pinned with `~`, so only patch updates come in automatically).
- Formatting is `oxfmt`'s job, configured in `.oxfmtrc.json`. Never hand-format; run
  `pnpm format`.
- Warnings are errors. If a rule genuinely doesn't fit, silence it narrowly with an
  `// oxlint-disable-next-line <rule>` comment plus a one-line reason, not by turning the
  rule off globally.

## Tests

- New behaviour needs a new test. Bug fixes need a test that fails without the fix.
- Tests live in `test/`, mirroring `src/`.
- Tests must not require a live database or network. Anything that does gets guarded with
  `describe.skipIf(...)` so CI stays green (see `test/database/db-query.test.ts`).
- Test files share workers (`isolate: false` in `vitest.config.ts`). `test/setup.ts` resets the
  module cache before each file, so `vi.mock` works as usual, but globals aren't reset. Anything
  a test changes on `process`, the environment or the clock has to be put back in an `afterEach`.
- Tests are typechecked, so type mocks against the real thing:
  `vi.fn<typeof Db.storeMention>()`, with `import type * as Db from '../src/services/database.js'`.

## Conventions

- Services in `src/services/` are imported as namespaces (`import * as db from ...`) so
  call sites read as `db.storeMention(...)`.
- Type-only imports use the top-level form: `import type { Foo } from '...'`.
- The `@atproto/api` record types are loosely typed. Narrow them with a local type and a
  `typeof` check rather than casting to `any`.
- Only the entry points read the environment, by calling `loadEnv()` from `src/config.ts` once
  and passing values down (ie: `createAgent(env.bluesky)`). Nothing else in `src/` reads
  `process.env` or calls `dotenv`. Limits worth tuning live in `src/config.ts` too.
- Never hardcode the bot's handle or DID; read them from `agent.session`, so forks just work.
- `src/services/database.ts` owns the one `PrismaClient`. Database access goes through it.

## Commits and PR titles

- Every commit message and PR title is one emoji, a space, then a short sentence-case summary:
  `🐛 Stop losing and double-answering mentions`, `🧹 Add linting, formatting, a pre-commit hook, and CI`.
- Pick an emoji that fits the change (🐛 bug fix, ✨ new feature, 🧹 cleanup, 🔧 config or small fix,
  ⬆️ dependency bump, 🪵 logging, 🧼 bad words list). `git log` has plenty more.
- No `feat:` / `chore(ci):` style prefixes.
- PRs are squash-merged, so the PR title becomes the commit on `main`. Same rule applies.

## PR descriptions

Short, and written in Dave's voice. If `~/.claude/DAVE_VOICE.md` exists, read it first; it beats
the voice notes below.

1. **Deploy steps go first.** If anything has to happen besides merging, open the description with a
   `> [!WARNING]` block listing the exact commands. Any change to `prisma/schema.prisma` counts:
   CI only runs `prisma:generate`, so someone has to run `pnpm db:push` against prod by hand. New env
   vars, GitHub secrets and one-off data fixes count too. No deploy steps, no block.
   Keep one-off deployment, migration and rollout instructions in the PR description, never in
   committed docs or README links to rollout docs. Put commands, ordering, conflict handling,
   verification and rollback details there; executable migration scripts can stay in the codebase.
2. Then one to three sentences: what it does, starting with a present-tense verb ("Fixes...",
   "Adds..."), and why.
3. A few bullets for anything a reviewer would miss in the diff, only if needed. Don't walk through
   every file.
4. One line on testing, and only what actually ran. If tests weren't run, say so.

Aim for under 150 words, not counting the deploy block. No `## What changed`-style headers, no
"Generated by" footer.

Voice: plain, casual words, like a teammate at the next desk ("I think", "we should", "just", "IMO").
Canadian spelling (colour, behaviour). Backticks on every identifier and file. `_underscores_` for
emphasis. "ie:", never "e.g.". Never em dashes or `--`; use a semicolon, brackets or a new
sentence. Never "This ensures", "leverage", or "robust". Honest about limits ("Note that this
doesn't fix X").

Example (PR #24, rewritten):

````md
> [!WARNING]
> After merging, run `pnpm db:push` against prod. It adds a unique index on `Mention.postId`, which
> fails if there are duplicate rows, so dedupe first:
>
> ```sql
> DELETE FROM "Mention" a USING "Mention" b
> WHERE a."postId" = b."postId" AND a."createdAt" > b."createdAt";
> ```

Fixes #11. Stops the bot from losing mentions that show up mid-run, and from replying twice to the
same one.

- The read cursor only moves past mentions we actually stored, so a failed one gets retried next run
- Mentions are handled one at a time, oldest first
- Paging stops at the first page of already-read notifications instead of walking the whole history

New tests cover the paging, the cursor and the upsert.
````
